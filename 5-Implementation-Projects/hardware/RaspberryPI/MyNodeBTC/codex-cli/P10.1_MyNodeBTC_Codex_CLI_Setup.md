# P10.1 — MyNodeBTC Host and Codex CLI Setup Findings

## Purpose

This document records the reusable implementation findings from preparing the existing MyNodeBTC Raspberry Pi host for Codex-based Jagports engineering work.

The durable AI OS infrastructure direction is defined in `00-Management/VISION_AI-OS.md`; current P10 work and sequencing are tracked through the corresponding GitHub Issues/Project. This file is implementation knowledge and setup guidance, not a replacement for the canonical Management workflow.

## Host baseline

- Hostname: `mynode-sby`
- OS: Debian GNU/Linux 12 (bookworm)
- Architecture: ARM64 / aarch64
- Kernel observed during setup: `6.12.96+rpt-rpi-v8`
- Hardware: Raspberry Pi 4B, 8 GB RAM
- Persistent storage: 1 TB SSD mounted at `/mnt/hdd`
- Root filesystem is comparatively constrained; persistent Codex/Jagports data should use the SSD rather than consume the existing MyNodeBTC application area unnecessarily.

## Existing MyNodeBTC installation

The host is an already operating MyNodeBTC installation, not a clean development host.

Therefore:

- Existing MyNodeBTC services and application directories are protected infrastructure.
- `/mnt/hdd/mynode` and other existing service/application directories must not become the Codex workspace.
- Codex setup must not assume that the host can be freely reconfigured like a disposable development machine.
- Privileged changes must be deliberate, minimal, and independently verified.

## Dedicated Codex storage boundary

MyNodeBTC uses an application-directory convention under `/mnt/hdd/<app>`.

The dedicated Codex area is therefore:

`/mnt/hdd/codex`

The intended initial boundary is:

```text
/mnt/hdd/codex        Codex-owned writable area
/mnt/hdd/mynode       Existing MyNodeBTC area; protected
```

The `codex` Linux account owns `/mnt/hdd/codex` and can create files there.

Do not move Codex work into `/mnt/hdd/mynode` merely because it already contains application data.

## Linux account and privilege boundary

A dedicated Linux user `codex` is used for Codex CLI work.

Administrative commands are performed by the administrative account, not by `codex`.

To enter the Codex login environment from an administrative shell, use:

```bash
sudo -iu codex
```

`su - codex` is not the working method on this host because the `codex` account has no usable local password.

The `codex` account does not have passwordless `sudo` capability. This is intentional and should remain the default security boundary.

Do not grant unrestricted root/sudo access to Codex simply to make setup easier.

## Docker boundary

Do not add `codex` to the Docker group merely for convenience.

Docker access is a privileged host boundary. If a future Jagports requirement genuinely needs Docker control, that requirement must be explicitly justified, approved, and implemented as a separate security decision.

## Codex CLI

Codex CLI was installed and verified during the setup exercise.

Observed version:

`0.150.1`

Codex CLI authentication was successfully established using the supported device-auth flow.

Authentication credentials and one-time device codes must never be recorded in repository files, Issues, Pull Requests, scripts, logs, or other project documentation.

## Verified local operation

The `codex` user successfully created a test file under `/mnt/hdd/codex`.

This verifies the intended initial local write boundary without granting Codex write access to the existing MyNodeBTC application directories.

## Setup principles established

1. Protect the existing MyNodeBTC installation.
2. Use a dedicated `/mnt/hdd/codex` application area.
3. Keep Codex running as the unprivileged `codex` user for normal work.
4. Perform host administration separately through the administrative account.
5. Do not grant passwordless sudo to Codex.
6. Do not grant Docker-group membership without an explicit approved requirement.
7. Prove the manual setup before automating it.
8. Define ownership, storage, privileges, start/stop behavior, health checks, logs, and backups before enabling persistent services.
9. Keep GitHub authoritative for source code, Issues, project records, decisions, and repository documentation.
10. Treat the Raspberry Pi as infrastructure rather than as the authoritative project-management system.

## Future MyNodeBTC Community Plugin / Extension

A future MyNodeBTC Community Plugin/Extension may automate the validated Codex/Jagports host preparation and service lifecycle.

Automation should come after the manual architecture and security boundaries are proven.

The future extension should be an infrastructure integration layer, not a replacement for Codex and not a mechanism for granting unnecessary host privileges.

Potential responsibilities to evaluate later:

- create/validate the dedicated Codex storage area;
- validate required Linux ownership and permissions;
- install or validate required runtime dependencies;
- start/stop approved persistent Jagports/Codex services;
- provide service health checks;
- expose operational logs;
- support safe recovery and backup procedures;
- fail closed when required prerequisites are not satisfied.

The exact MyNodeBTC plugin/extension mechanism must be inspected before implementation; no plugin architecture should be assumed from the existence of the MyNodeBTC service stack alone.

## Relationship to P10

This work refines P10.1, `Prepare Linux environment`, from a generic clean-host setup task into a constrained integration task:

`Existing MyNodeBTC host → protected infrastructure → dedicated Codex boundary → least privilege → verified CLI operation → persistent-service design → optional automation`
